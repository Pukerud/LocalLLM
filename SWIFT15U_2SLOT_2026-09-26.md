# Swift 1.5 uncensored Q8: four-RTX-3090 capacity and MTP check

Tested on `.69` on 2026-09-26 with the installed `4cbe8b07` llama.cpp runtime,
`Swift-1.5-Qwen3.8-27B-Uncensored-Dynamic-MTP-UD-Q8_K_XL.gguf`, BF16 vision
projector, Q8_0 K/V, flash attention, layer split across four RTX 3090s,
`xhigh` reasoning and native MTP. The server model identity was checked through
`/v1/models` after each switch. The original one-slot server was restored and
verified after each probe batch.

## Slot capacity

| Slots | Aggregate context | `/slots` context per slot | Short text / vision / simultaneous requests | Outcome |
| ---: | ---: | --- | --- | --- |
| 1 | 262,144 | 262,144 | text and vision passed | Existing baseline |
| 2 | 524,288 | 262,144 each | text, vision, two simultaneous text requests passed | Selected |
| 3 | 786,432 | 262,144 each | text, vision, three simultaneous text requests passed | Works but less headroom |
| 4 | 1,048,576 | unavailable | CUDA device 3 ran out of memory while allocating the MTP KV cache | Do not use with Q8 KV |

The three-slot run used approximately 18.2, 16.7, 17.1 and 22.1 GiB per GPU.
Free VRAM summed across cards is not interchangeable; the fourth Q8-KV slot
failed on GPU 3. These checks establish configured full-size *capacity* and
short inference, not successful generation from a 262K-token prompt.

## Exploratory decode tuning

All rows below used two 262K slots and Q8 K/V. The short request returned the
correct answer with `finish_reason=stop` in five serial trials; its median is
shown. Coding and narrative probes each generated exactly 512 tokens and hit
the length limit. Their medians use the last three of five trials and are
**fixed-budget decode throughput only**, not completed-answer or quality scores.

| MTP draft depth | Short, tok/s | Coding 512-token decode, tok/s | Narrative 512-token decode, tok/s |
| ---: | ---: | ---: | ---: |
| Off | 25.89 | — | — |
| 2 | 54.10 | — | — |
| **3 (selected)** | 60.65 | **45.88** | **50.30** |
| 4 | 64.41 | 45.49 | 49.49 |
| 5 | 66.47 | 42.96 | 48.64 |
| 6 | 64.49 | 40.22 | 45.07 |
| 7 | 63.79 | 38.12 | 43.68 |

Depths 4–5 help the short request, but depth 3 is faster in both longer probes.
The retained depth 3 is therefore the conservative balanced setting. No model
weight, KV precision, reasoning level or vision reduction is proposed. Vision
and two simultaneous short requests returned correctly at every tested depth;
The final HiveOS-managed service also passed two simultaneous prompts of
6,675 and 6,676 input tokens, returning their distinct codewords correctly
with `finish_reason=stop`. Concurrent prompts near the 262K limit have not
been tested.

## Managed handoff verification

The installed `llm-hosting` custom miner starts `swift15u-q8` with two
262,144-token slots, Q8_0 K/V, BF16 vision, `xhigh`, and native MTP depth 3.
With no Docker rental container present, `osn.service` remained active while
the HiveOS custom miner ran. `miner stop` removed the server and left
`osn.service` active; `miner start` restored the same Swift model and both
262,144-token slots. Five short text requests, vision, two simultaneous short
requests, and the two ~6.7K-token concurrent requests all returned normally.

The current launcher already uses flash attention and layer split. Upstream
llama.cpp documents that context is an aggregate server allocation across
parallel slots, and that experimental tensor split needs unquantized KV,
which conflicts with this Q8-KV objective. See the
[server options](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md),
[speculative decoding](https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md),
and [multi-GPU guidance](https://github.com/ggml-org/llama.cpp/blob/master/docs/multi-gpu.md).
